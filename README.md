# DokuEMS GrapesJS Designer — Proof of Concept

This is an **isolated, runnable frontend proof of concept** for a free/open-source visual invoice, receipt and PCR designer using GrapesJS Core (`BSD-3-Clause`). It is not wired to the DokuEMS repository or production APIs because the DokuEMS working tree is not mounted in this environment.

## Run locally

Requirements: Node.js 20+ and npm.

```powershell
npm.cmd install
npm.cmd run install:browser
npm.cmd run dev
```

Open `http://127.0.0.1:5181/`. The `dev` command starts both the Vite editor and the local PDF service. The first browser install downloads Chromium for Playwright and is only required once per Playwright browser cache.

For tests and a production frontend build:

```powershell
npm.cmd test
npm.cmd run build
```

`npm start` serves the built `dist` application and the PDF endpoint on port 5182. Run `npm run build` first.

## Included in this proof of concept

- Three synthetic template seeds: Invoice, Payment Receipt and Patient Care Report (PCR).
- GrapesJS Core editor with a light-themed DokuEMS component palette and properties inspector. The palette now provides 28 tools across Text & Fields, DokuEMS Fields, Tables & Totals, Codes & Signatures, Layout and Media.
- Dedicated Label, Text/Paragraph, Heading, Data Field, Date Field, Amount/Currency, Multiline Data Field, Organization Info, Invoice Information, Bill To/Customer, Service Details, Charges/SST Table, Payment Table, Invoice Totals, QR placeholder, Barcode placeholder, Signature Block, Approval Stamp, Checkbox/Tick, Divider, Bordered Box, Two/Three Columns, Notes/Terms, Page Number placeholder, Vertical Spacer, Page Break and Image/Logo tools.
- Flow-based HTML/CSS layout. Text wraps within cards and table cells instead of using fixed-position rectangles for every element.
- Undo/redo, component selection, drag-and-drop, styling, binding traits, layer view, zoom, Fit Width and Fit Page.
- Save and Reload for browser-local drafts, plus project JSON export.
- **PDF preview generated by a local Node.js + Playwright/Chromium service** from the current unsaved HTML/CSS design. The PDF is displayed in an embedded PDF viewer and can be downloaded; there is no HTML preview modal.
- An A4 print stylesheet that keeps the page size independent of editor zoom, prints background colours, repeats table headers where supported, and allows long flow-based content to paginate.

## Important limits

**This is not connected to live DokuEMS.** It does not call the template API, publish versions or access business records. The PDF is generated by local Playwright/Chromium from the prototype’s current HTML/CSS and synthetic sample content. It is a real PDF preview, but it is not yet a production DokuEMS rendering path and does not replace the current production renderer.

All displayed values are synthetic. The QR and barcode visuals are placeholders, not scannable codes. The selected QR/barcode controls expose DokuEMS binding metadata; real QR/barcode generation still requires an approved encoder integration. DokuEMS bindings and the repeat-row markers are proposed integration contracts for the proof of concept; they must be reconciled with the actual approved DokuEMS binding catalog before production use.

## Proposed production architecture

1. Use GrapesJS Core for editing and store its project JSON plus the generated HTML/CSS in a versioned template format. Do not store only the exported HTML: GrapesJS recommends retaining project JSON for reliable editor reloads ([Storage Manager docs](https://grapesjs.com/docs/modules/Storage.html)).
2. The .NET API validates the permitted component set, CSS and binding tokens. It must not execute arbitrary scripts or trust uploaded template HTML.
3. The .NET API resolves authorized data bindings and expands repeating collections into HTML using a strict allowlist and HTML encoding.
4. A server-owned Playwright/Chromium service generates A4 PDFs from the validated HTML/CSS ([Playwright PDF docs](https://playwright.dev/dotnet/docs/api/class-page)). No client receives database credentials, and the renderer must block arbitrary external network/resource access.
5. Use the existing publication, authorization, audit, retention and pinning rules. Add a renderer/format discriminator per template version.
6. Keep the legacy PDFsharp renderer available for legacy fixed-layout template versions and pinned historical documents until an explicit, tested migration policy exists. A new renderer must not make old pinned templates unreadable.
